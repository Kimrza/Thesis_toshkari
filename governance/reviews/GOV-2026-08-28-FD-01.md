blocking defect of the same structural class: an obligation asserted by a consuming
unit against a producing unit whose own finalized design does not carry it. The
pre-metric prediction-hash receipt has two consumers and no producer; the
chokepoint's one-door rule is contradicted by three test modules present in the
workspace today; `models-and-baselines` specifies the train-only-transform guard
against `FeatureBundle` fields ADR-11 retired on 2026-08-23; `features-and-splits`

`train_start`, while never naming the blocker (BLK-09) it owns; and
`test_clean_run.py` is specified to execute scripts §13.2 places only behind G-P2.
This is a process verdict on design completeness, not a judgement on the science —
the physics, target lineage, estimand, mask mechanics and custody architecture were
each independently found sound, and every blocking defect is curable by adding rules
inside stage 3.1 before any code exists.

## Findings

### Recommendation 1 — The pre-metric prediction-hash receipt has two consumers and no producer

- **Category**: Compliance
- **Severity**: `Critical` (reviewer grade: `BLOCKER`)
- **Finding ID / reviewer**: `VAL-01` — Validation Auditor (**veto exercised**)
- **TEC gate / AI-DLC stage**: G-06 primary, G-05, G-09 / 3.1 → 3.5
- **Requirement**: Vision §8.3 ("generated once, hashed **before** any metric, written once"); Vision §13.1 row G-06 (evidence: "Registry entry, **prediction hash**, metrics, artifact hashes"); TE §13.4; `requirements.md` FR-P1-05-12
- **Evidence**: `evaluation-and-comparison/domain-entities.md` § 5 (~line 136) and `business-rules.md` R-109 limb 1 (line 270) both state "Recording the hash is **`06`'s act**"; `statistical-inference` R-113 limb 3 (lines 69–71) consumes identically. Across `models-and-baselines`' four artifacts, which own `scripts/06_train_and_predict.py`: `PredictionHashReceipt` = 0, "prediction hash" = 0. Across all 48 artifacts: `prediction_hash` = 0, `prior_period_exposure` = 0

**Issue** — Two units refuse to compute a `DEC` metric without a verified receipt
whose `recorded_at_utc` precedes the call. No unit designs the act of creating that
receipt, the registry column carrying it, or `prior_period_exposure`, which
FR-P1-05-12 names as a positive obligation.

**Importance** — Hash-before-metrics is the control that makes the one-shot locked
evaluation auditable. It is the difference between a prediction that was fixed
before anyone saw a score and one that might not have been.

**Risk** — As designed, G-06 cannot execute: every `DEC` metric entry point raises
`LockedTestError` forever. That is fail-closed and not itself a breach. The hazard is
the repair — the cheapest way to clear the deadlock at implementation time is to
write the receipt inside `07_evaluate_and_report.py`, in the same process that
computes the metric, which makes "the receipt precedes the metric" self-certifying
and turns the control into a formality that passes its own test.

**Possible Solutions**

1. Assign the write to `06` in `models-and-baselines`, as R-109 already asserts: the
   one-shot `DEC` prediction write emits a `PredictionHashReceipt`
   (`prediction_path`, `sha256`, `recorded_at_utc`, `run_id`, `partition_id`),
   durably flushed before `06` exits; `06` refuses to exit with a `DEC` prediction
   file and no receipt; receipt and `prior_period_exposure=true` reach the registry
   row; negative control — a `DEC` prediction written with no receipt raises in `06`,
   not later in `07`.
2. Assign the write to `governance-guards`' `locked_test.py`, beside `open_restricted`.
3. Draft it as a two-half contract on the R-103/BLK-08 pattern: half A binding in
   `evaluation-and-comparison` (already written), half B drafted complete for
   `models-and-baselines` pending adoption, registered as an exit condition on 3.1
   for both owners.

**Comparison** — (1) makes three artifacts true instead of leaving them asserting an
obligation nobody carries, and keeps writer and reader in different processes, which
is what makes the ordering meaningful; its cost is that `models-and-baselines` is
frozen READY, so it needs a re-entry or an annexed addendum. (2) puts both halves of
the custody record on one module and reopens no frozen unit, but `locked_test.py`
never sees the prediction object — it would hash a path handed to it by a caller, so
the caller still chooses *when* to call and the self-certification risk returns one
level up. (3) is the right *procedure* for landing (1) in a frozen unit without
editing it unilaterally, and this stage has already established that pattern; it adds
a fifth open blocker and defers the fix.

**Recommendation** — (1) for the substance, with (3) as the adoption vehicle. The
smallest acceptable remediation is one rule in `models-and-baselines` naming `06` as
the writer with the refusal-to-exit control.

- **Closure evidence**: `PredictionHashReceipt` present in `models-and-baselines/business-rules.md`; `prediction_hash` and `prior_period_exposure` present in the owning unit's design; a stated control proving `07`/bootstrap cannot be the writer
- **Owner / due gate**: `models-and-baselines` unit owner (writer rule) + `foundation` (registry column) — this stage's gate, hard-blocking before G-09

**Decision Required** — `Approve` / `Reject` / `Modify` / `Postpone`

### Recommendation 2 — The chokepoint's one-door rule is contradicted by three live test modules, with no carve-out anywhere

- **Category**: Security
- **Severity**: `Critical` (reviewer grade: `BLOCKER`)
- **Finding ID / reviewer**: `VAL-02` — Validation Auditor (**veto exercised**)
- **TEC gate / AI-DLC stage**: G-05, G-06, G-09; WS-18/TA-18 evidence / 3.1 → 3.5, 3.6
- **Requirement**: `evidence/DECISIONS.md` D-15 (the restricted root is a governance boundary held only while exactly one code path reaches it); `component-dependency.md` § Shared resources ("nothing else may construct a path into it"); TE §12
- **Evidence**: `governance-guards/business-rules.md` R-28 (line 623): "a **static check asserts no module outside `locked_test.py` contains the restricted-root literal**", negative control at line 641; restated unqualified at four further sites in that unit and echoed in `acquisition`, `inventory-and-registry` and `foundation` — ten sites, no carve-out. Workspace today: `tests/test_acquisition_window.py:46`, `tests/test_phase_boundary.py:49`, `tests/test_release_hashes.py:49` each define `RESTRICTED_DIR`; two read content beneath it (`test_release_hashes.py:137`, `test_acquisition_window.py:195`). `governance-guards` read two of those three modules directly (`business-logic-model.md:55`) and quotes `test_acquisition_window.py`'s internals at `business-rules.md:576`

**Issue** — The design's pass condition is that exactly one module holds the
restricted-root literal. Four hold it today (three tests plus the future
`locked_test.py`), so the design's own negative control is satisfied by the workspace
as it stands — and the unit that wrote the rule had read the violating modules.

**Importance** — D-15's boundary, in R-28's own words, "does not weaken slightly; it
ends" if a second path exists. Every custody guarantee downstream rests on the
one-door property.

**Risk** — Two outcomes, both bad, and nothing chooses between them. Implemented as
written, the static check fails against the project's own custody tests and will be
relaxed under schedule pressure — most likely to a substring exemption broad enough
to re-admit arbitrary callers. Implemented with an undeclared `tests/` exemption, test
modules read December bytes with no `AccessRecord`, which is the RES-04 hazard
`evidence/experiment_registry.md:79–83` already records as "BLK-07's registered hazard
occurring in fact rather than in principle."

**Possible Solutions**

1. An enumerated `tests/` exemption inside R-28: named modules may hold the literal,
   listed exhaustively, each required to route any *content* read beneath the
   restricted root through `open_restricted` or a synthetic fixture root, with the
   static check asserting the list's membership exactly (R-26's already-accepted
   enumerated-exclusion technique).
2. Refactor all test modules to obtain the restricted root only from `locked_test.py`,
   keeping the literal in one file.
3. Redefine the check as "no **`src/`** module outside `locked_test.py` contains the
   literal", leaving `tests/` out of scope.

**Comparison** — (1) keeps the check implementable *and* truthful, and a mislabelled
module stays detectable; it concedes that more than one module holds the literal, so
it must be stated as a narrowing rather than hidden. (2) preserves the letter of
"exactly one module" but is circular for `test_locked_test_guard.py`, which would
import the module under test to find the thing it tests, and an imported constant
still yields a readable path with no `AccessRecord` — the custody gain is cosmetic.
(3) is trivially implementable and is what will be chosen by default if nothing is
decided, and it converts the largest known hole into a permanent blind spot.

**Recommendation** — (1). It also composes with the already-registered RES-04
obligation: an exempt module that reads content still owes a pre-read access row.

- **Closure evidence**: R-28 carries an enumerated exemption list; a control that adding a module fails the membership test; a stated route for `test_locked_test_guard.py`; the three existing modules classified as exempt-and-logged or refactored
- **Owner / due gate**: `governance-guards` (R-28) with `features-and-splits` (R-82's module route) — this stage's gate; prerequisite of BLK-07's resolution

**Decision Required** — `Approve` / `Reject` / `Modify` / `Postpone`

### Recommendation 3 — `models-and-baselines`' leakage guard targets `FeatureBundle` fields ADR-11 retired

- **Category**: Architecture
- **Severity**: `Critical` (reviewer grade: `BLOCKER`)
- **Finding ID / reviewer**: `IMPL-01` — Implementation Reviewer (**veto exercised**)
- **TEC gate / AI-DLC stage**: blocks 3.5 for `06_train_and_predict.py`; §18.3 preflight (train-only transforms); G-09 authorisation to write `src/models/train.py`
- **Requirement**: `component-methods.md` ADR-11 (2026-08-23): `FrameSpec.role: Literal["train","score"]` (line 542), `FeatureBundle.spec: FrameSpec` (line 558), `bundle.spec.role`/`spec.partition_id` throughout (lines 626, 643, 719). `purpose: str` exists only on the locked-test access-log entity (`"coverage_audit" | "regime_audit" | "locked_evaluation"`, line 270) — not a `FeatureBundle` attribute, and `"evaluate"` is not one of its values
- **Evidence**: `models-and-baselines/business-logic-model.md:33–43` (W-1) and `business-rules.md:31–43` (R-90): "It checks `bundle.fold_id` equals the fold being scored, `bundle.purpose` equals `evaluate`, and `bundle.transform_id` is present." Mirrored at `domain-entities.md:353` and `functional-design-questions.md:30–36`. The same unit's W-2 (line 96) correctly uses ADR-11's `Partition`/`partition_id` vocabulary. The only pass run after the retirement (`business-logic-model.md:573–620`) scoped itself explicitly to regression-only and never re-checked W-1/R-90 against the live contract

**Issue** — The design specifies a leakage guard — one of §18.3's ten named critical
items, and the negative-control pair for the project's central leakage-prevention
rule — using an attribute name (`fold_id`), a field name (`purpose`) and an enum
value (`evaluate`) that do not exist on the object it will receive.

**Importance** — An implementer following this text cannot write `06`'s stamp-match
function against the real `FeatureBundle`. The READY verdict standing on this unit
never assessed ADR-11 fidelity for its most safety-critical rule.

**Risk** — Either an implementer invents a `purpose`/`fold_id` shim
`component-methods.md` does not sanction (a silent contract deviation), or stops and
reports per §18.3. Either way the unit's stated READY does not hold for that rule.

**Possible Solutions**

1. Rewrite W-1/R-90 and the two mirrored passages to state the check as
   `bundle.spec.partition_id == partition_being_scored.partition_id` and
   `bundle.spec.role == "score"`, matching ADR-11 exactly, and re-derive the negative
   controls in that vocabulary.
2. Carry it to the gate as a disclosed defect and let the human rule on whether to
   redo now or accept it as a tracked exit condition alongside BLK-03/BLK-08.

**Comparison** — (1) is small and targeted and disturbs no other section of an
otherwise-verified unit; it reopens a receipt the workflow has treated as closed
since 2026-08-24, which this project's own learned practice treats as a non-trivial
recovery path. (2) respects the rule that a finding is quoted at the gate rather than
applied on its own strength, but advances the stage with an unimplementable critical
test on the books.

**Recommendation** — (2) is the correct route for *this report* — the finding is the
deliverable. The seat's own recommendation to the human is explicit, and this Chair
endorses it: treat this as build-blocking rather than as gate input to weigh, and
authorise a targeted redo of W-1/R-90 before 3.5 starts, not a general
re-litigation of the unit.

### Recommendation 4 — BLK-09 is unmet and de-labelled in its sole owning unit; the range-equality check has no lower bound

- **Category**: Design
- **Severity**: `Critical` (reviewer grade: `BLOCKER`)
- **Finding ID / reviewer**: `CHAIR-03` — Review Chair; `ML-01` — ML & Statistical Methods (two seats, independently derived)
- **TEC gate / AI-DLC stage**: G-04, G-05; 3.1 exit condition / 3.1 → 3.5
- **Requirement**: `unit-of-work.md:867` assigns BLK-09 to `features-and-splits` **solely**; `:857` — "Status: **Open.** Exit condition on stage 3.1"; `:333` — "**No affected unit may complete or exit 3.1 without its approved contract**"; `GOV-2026-08-22-REM-01` REM-02 (Options 1 + 3 approved — exit condition, not entry); TC-03e (no scientific constant in source)
- **Evidence**: derived across all four `features-and-splits` artifacts by both seats independently: `BLK-09` = **0**, `train_start` = **0**, `BLK-08` = **0**, `inverse` = **0**. `domain-entities.md:436` gives the live `Partition` shape — `partition_id`, `kind`, **`train_end`**, `validation_month`, `embargo_hours=24` — with no `train_start`. `domain-entities.md:231` and `:515` nonetheless keep the raise: `fit_transforms` raises `LeakageError` "when the bundle's scored range is not exactly `partition`'s **training range**". `business-logic-model.md:277–280` asserts "equality **is checkable** because `fit_transforms` takes the `Partition` itself in scope". `component-methods.md:904–906` — the upstream contract's own closing note — states: "`Partition` carries no `train_start`, so the training-range comparisons in `fit_transforms` and `build_features` rest on an unwritten January-1 convention (Major)." Five sibling units record "BLK-09's `train_start` resolution (`features-and-splits`)" as a dependency owed there

**Issue** — BLK-09 is not merely unresolved; it has been **de-labelled**. The ADR-11
rebuild carried the dependent raise forward and dropped the blocker's name from the
owning unit's entire artifact set, while affirmatively asserting the check is
executable. With only `train_end` in scope, `[scored_start, scored_end] == training
range` has no lower bound to compare against.

**Importance** — In `unit-of-work.md` a reader at least finds the registered defect;
in the terminal-READY design a 3.5 implementer finds only an unexecutable check. This
is the fitting side of NFR-LEAK-01 and one of §18.3's ten named critical tests.

**Risk** — Three implementer options, all bad: hard-code `2022-01-01` (breaches
TC-03e and `project.md` § Forbidden); derive `train_start` from the earliest row
present, which degenerates the equality check into a tautology — a check that can
never fire, indistinguishable from one that passes, and the unit's own stated
anti-pattern; or stop. Under the tautology path a transform fitted on a strict subset
of the declared training range is accepted, stamped with the partition id, and passes
the apply-side identity check, so the standardization constants differ from the
declared fold protocol with no downstream symptom.

**Possible Solutions**

1. Add `train_start: date` to `Partition`, sourced from `configs/data.yaml`, and read
   both bounds from the `Partition` in `fit_transforms`; restore a BLK-09 paragraph
   in the owning unit's Blockers; add a negative control that a strict-subset `train`
   bundle raises.
2. Keep `Partition` unchanged; weaken the raise to `scored_end == partition.train_end`
   only, and state the lower bound as unchecked.
3. Derive the training range from `ConfigSnapshot` inside `fit_transforms`.
4. Record BLK-09 as explicitly deferred past 3.1 with owner approval, artifacts
   unchanged.

**Comparison** — (1) makes the check do what all three artifacts say it does and puts
the constant where TC-03e requires; it amends the approved `component-methods.md`
contract, so it needs the owner's ruling. (2) needs no amendment and still catches
the over-wide-fit (leaking) direction since `train_end` bounds it, but accepts the
strict-subset fit permanently and closes BLK-09 by lowering the bar rather than
meeting it. (3) pays (1)'s amendment price with worse locality, splitting the
partition's definition across two objects. (4) avoids the receipt-floor mechanics but
directly reverses REM-02's approved ruling, which `project.md` c12 forbids reopening
without a new argument or an explicit human decision — available to the human, but
only knowingly.

**Recommendation** — (1), bundled with Recommendation 7's redo so one re-entry closes
both of that unit's outstanding exit conditions. (2) is a legitimate fallback only if
the owner explicitly accepts the strict-subset fit on the record.

- **Closure evidence**: `grep -c "train_start\|BLK-09"` non-zero in `features-and-splits/domain-entities.md`; a BLK-09 status paragraph present; a strict-subset negative control stated
