# Application Design — Stage Memory

Observation diary for stage 2.6 (application-design). Maintained while the stage
runs; read by the §13 learnings ritual before the approval gate.

## Interpretations

- 2026-08-21T18:40:00Z — Treated this stage as **interface design inside a frozen module tree**, not architecture selection. TE §12 fixes the repository layout to individual file level — six `src/` packages, every module named, most with a one-line responsibility — and TC-03e, §8.3 and the affirmed team practices fix the language, the linter, the config set and the two execution platforms. `components.md` and `services.md` are therefore substantially a transcription of a frozen structure with its boundaries made explicit; the genuinely open design work is the method surface (§12 fixes no signature), the enforcement mechanism for each hard boundary, and the handful of responsibilities §12's tree does not assign to any module.
- 2026-08-21T18:40:00Z — Did not ask the stage's default questions on service communication patterns (sync/async, REST/gRPC/events), service scaling characteristics, data ownership across services, or UI component structure. This is a single-process, CPU-only, offline batch pipeline with no services, no network surface and no user interface: `services.md` describes the nine stage scripts as pipeline stages rather than deployable services, and the design agent's UI contribution is `N/A` with that reason recorded. Asking the default menu would have produced answers with nothing to attach to.

## Deviations

- 2026-08-21T18:40:00Z — Recorded a genuine gap in the frozen tree rather than silently placing it: **no §12 module owns config loading, the per-run four-config snapshot, or the config hash** that §13.1 requires of every run, and `team.md` states there is no seventh `utils` package to put it in. Raised as a question rather than resolved by inference, because choosing a home for it is a boundary decision and TC-03e constrains where scientific constants may live.

## Tradeoffs

- 2026-08-21T19:30:00Z — Leaned the design on making violations **unrepresentable in the interface** rather than forbidden in prose: `fit_transforms`/`apply_transforms` as two functions, `three_seed_mean` rejecting a wrong seed set, `count_storm_events` taking `release_grade` and `source` as required arguments. The architecture reviewer then showed two of those claims do not hold as written (see Open questions), which is the right outcome for a single advisory pass and the reason the claim was worth stating explicitly enough to be falsified.
- 2026-08-21T19:30:00Z — Wrote `services.md` around the nine stage scripts and recorded UX as `N/A` with its reason, rather than omitting the design-agent perspective silently. The alternative — answering the stage's default questions about sync/async, scaling and UI structure — would have produced design with nothing to attach to, since there is no service, network surface, database or user interface in this pipeline.

## Open questions

Harmless as filenames, but the clean-run sequence in §13.2 and the `NN_verb_noun.py` convention both key on the ordinal, so the two-phase collision needs an explicit reading before `code-generation` builds the runner.
- 2026-08-21T18:40:00Z — Carried in from stage 2.3, unresolved and bearing on this stage: § Known defects row 12 (the `plumbing_7day` station count) blocks the fixture manifest that `run_walking_skeleton.py` reads, and the advisory `NOT-READY` finding on FR-P1-05-18 (no criterion tests the storm-event count's source) lands on `src/evaluation/regimes.py`, which this stage must give an interface.
- 2026-08-21T19:35:00Z — **Three verified findings from the advisory pass, all confirmed against the artifacts before the receipt was recorded, and none fixed here** (advisory verdicts are terminal, so they are gate input rather than builder input). (1) `three_seed_mean(predictions)` takes no seed set, so it cannot check the seeds are "exactly the frozen set" without either hardcoding `{1337, 2024, 7}` — which TC-03e forbids — or weakening to a distinctness check that admits a wrong-but-distinct triple. `vector_block_bootstrap(seed: int)` got this right for the same problem, which makes the omission a straightforward inconsistency. (2) `fit_transforms(train: DataFrame, *, fold)` does **not** make full-dataset fitting unrepresentable: `train` is an unconstrained `DataFrame`, so `fit_transforms(all_data, fold=f)` is perfectly writable. The two-function split blocks only the single-call convenience shape, and ADR-01's "enforced by shape rather than by review" overstates what the types deliver. (3) ADR-10 claimed REQ-ENG-4's test-module count must move in four places; only two carry it. Verified: `requirements.md` § Requirements with no testing row holds **40 untested requirement IDs**, not a module count, and `team-practices.md` § Testing Posture says **17 modules** (the §12-enumerated set, deliberately excluding amendment-added modules), not 18.
- 2026-08-21T19:35:00Z — Finding 3 is the **third** count I have asserted this session without checking it against the source, after `DATA-21`'s "thirteen field groups" and the untested-list "23 entries". The pattern is now well evidenced: a count reused from adjacent prose rather than derived from the artifact. The mitigation that has actually worked every time is deriving counts programmatically from the artifact and printing them, which is what caught the 39-versus-38 and 40-versus-39 discrepancies correctly in the same session.
